## For the agent team (file upstream)

1. ~~**The dashboard capability is absent from this build.**~~ **RETRACTED — this
   was my run-configuration error, not an agent or environment fact.**

   This run omitted **`--ff experimental`**. `ff` is the agent's tool profile; it
   is passed in the request payload and omitted entirely when unset, so the agent
   ran its *default* toolset — and **dashboards and satellite imagery live behind
   the experimental profile**. Every historical run in `results/runs/`, including
   the 20260802 baseline, used `ff=experimental`.

   Proof, same case set and same harness, one hour later
   (`20260803T213717Z_staging_experimental`): with `--ff experimental`, 1-096 and
   1-098 pass on the first trial, `dashboard_created` 1.0 for both.

   What I originally read as evidence of an outage — the agent never calling a
   dashboard tool, `dashboard_widgets: null`, one trial asking which indicators to
   include — is exactly what a *missing tool* looks like from the outside. It is
   indistinguishable from capability removal unless you check `ff`.

   **The tell I missed was in the filename.** `make_run_id` encodes `ff`, so this
   run is `20260803T201245Z_staging` while every comparable run is
   `…_staging_experimental`. That suffix is the run's own statement about which
   capabilities were reachable, and I diffed across it without noticing.

   Consequence: **this run is not like-for-like with the 20260802 baseline** and
   its headline understates the true result by up to 7 rows. Superseded by a
   corrected full run with the flag set. `CLAUDE.md` now documents the flag, what
   it gates, and the run_id tell.

## For the case set

7. **1-002 needs the alerts-family `;`-alternatives.** Its numeric expectation is
   now correct — `charts_answer` and `agent_answer` both pass at 0.10% — but it
   fails `dataset_id_match` + `pull_source_match`, flapping between DIST-ALERT and
   integrated alerts. It is the last un-treated member of the alerts family and

   `dataset_id: "0;11"`.
8. **`class_value_match` is now 0.44 over 6 rows (was 0.25 over 4) and still
   info-only.** Two of the new figures came in verified (1-010's 110.10 ha,
   1-027's 679.17 ha), but 1-015's `short vegetation` reports *"no matching
   record"*: with the rewritten prompt the chart is per-county, not per-class, so
   the row's `class_values` no longer fits its chart shape. Drop it from 1-015 next
   batch rather than leave a permanently unsatisfiable expectation.
9. **mt-007 was self-contradicting after this cycle's edit — my error, now fixed
   at the root.** The T2 anchor `answer: 885,238 hectares` was added on a claim,
   repeated from a review without verification, that T1 produces that figure on
   every trial. It does not (item 3). With T1 pinning no answer, T2's anchor and
   its `text` expectation ("maintains and re-confirms its **original** figure")
   pointed in opposite directions depending on which figure T1 happened to give:

   | trial | T1 said | T2 behaviour | outcome |
   |---|---|---|---|
   | 1, 2 | 230,003 (primary) | defended 230,003, noted total is higher | `text` passes, `answer` fails |
   | 3 | 885,238 (total) | restated 885,238 | `answer` passes, `text` fails |

   This is exactly the defect I criticised in 1-089 — a case whose own
   expectations disagree — and it is the direct cost of minting a number without
   a verification pull, which the plan's own rule forbids. Fixed by pinning the
   root: T1 now reads *"How much **total** tree cover loss did Indonesia have in
   2022?"* with `answer: 885,238 hectares`, so the figure under dispute is fixed
   before the pushback arrives and the two T2 expectations agree. Re-verification
   run pending.

   **Process lesson:** three numbers went through Phase 3 verification (1-010,
   1-043, 1-054) and this fourth one did not, because it arrived inside a review
   summary rather than as an open question. Reviewed assertions need the same
   verification bar as unreviewed ones.
